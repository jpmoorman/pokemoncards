# Pokémon Card Scanner

A free web app for your phone: point the camera at a Pokémon card and it identifies the card and shows what it's worth. There's no app-store install, no account and no subscription.

**How it identifies a card**

1. Text recognition ([PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR) PP-OCRv6 tiny models on [onnxruntime-web](https://onnxruntime.ai/), with [Tesseract.js](https://github.com/naptha/tesseract.js) as a fallback on older phones) runs **on your phone**. It reads the card's
   - **name** (the biggest text at the top),
   - **collector number and set size** (`125/197`, `4/102`, `TG05/TG30`, `SWSH050`),
   - **set code** printed on Scarlet & Violet and newer cards (`OBF EN`, `POR EN`, `PBL EN`, `30C EN`, …).
2. Those clues are matched against every English card ever printed, from Base Set to the newest sets.
   Older cards that only have a set *symbol* are matched by **set size + number + name**
   (for example, `4/102` + "Charizard" can only be Base Set Charizard).
   New sets show up automatically: the set list comes live from the card database.
3. You get the best match plus other likely matches with pictures. Tap one if the first guess is wrong.
   You can also correct what the camera read and tap **Re-match**.

**Prices and specialty markings**

Each printed version gets its own price: Normal, Reverse Holo, Holo, **1st Edition**, Shadowless, promo stamps and Jumbo.
- **TCGplayer** (USD): market, low, mid and high
- **Cardmarket** (EUR): trend, average, 7-day and 30-day
- One-tap links to **eBay sold listings** (what cards actually sold for), eBay active listings, TCGplayer and
  PriceCharting (graded values).

Card data and prices come from the free [TCGdex API](https://tcgdex.dev). Brand-new sets can take a few weeks to get prices; until then the app says "No price yet" and points you to eBay sold listings. eBay doesn't offer a free API that works from a browser, so the app opens eBay's own search, filtered to sold listings.

**Also included:** manual search, a collection list with a running total, CSV export, a backup file of your saved cards and trade (Saved → Export backup / Import backup), and it works offline after the first load. You can add it to your home screen like a normal app.

On iPhone, add it to the Home Screen: Safari can delete a website's saved cards after a while without a visit, and the Home Screen app keeps them. The Home Screen app has its own storage, so export a backup in Safari first and import it there (the app reminds you once).

## Use it on your phone

The app is a static website, so it needs to be hosted somewhere with **HTTPS**, because phones only allow camera access on secure sites. GitHub Pages is free:

1. On GitHub: **Settings → Pages → Build and deployment → Source: GitHub Actions**.
2. Push to `main`. The workflow in `.github/workflows/pages.yml` runs the tests and publishes the site.
3. Open `https://<your-username>.github.io/<repo-name>/` on your phone.
   - **iPhone (Safari):** Share → *Add to Home Screen*.
   - **Android (Chrome):** ⋮ → *Add to Home screen* / *Install app*.

The first time you open it, it downloads the card list (a few MB) and the text-recognition engine (about 5 MB). After that, both are cached on the phone.

## Tips for good scans

- Lay the card flat, in good light, and fill the on-screen frame with it.
- Glare on holo cards and sleeves is the most common problem. Tilt the card slightly or turn on **Light** (Android).
- If the camera keeps missing, use **Photo**. Your phone's camera app takes sharper pictures than the live preview.
- The *Raw text read from the card* section at the bottom of a result shows exactly what the scanner saw.

## Development

No build step: plain HTML, CSS and ES modules.

```bash
npm install          # only needed for tests
npm start            # http://localhost:8080 (the camera works on localhost)
npm test             # unit tests: parsing, matching, prices
npm run test:e2e     # headless Chromium + real OCR on generated card images
```

| File | What it does |
| --- | --- |
| `js/ocr.js` | Camera, finding the card, which areas to read and which way up |
| `js/ppocr.js`, `js/ocr-worker.js` | PP-OCR text reading in a worker (models in `models/`, runtime in `vendor/`) |
| `js/ocr-tesseract.js` | The Tesseract reader, used only where PP-OCR can't run (iOS before 16.4) |
| `js/parse.js` | Pulls numbers, set codes and the name out of OCR text |
| `js/match.js` | Fuzzy-matches the clues against the card list and ranks the candidates |
| `js/prices.js` | Prices per version (1st Ed., reverse holo, …) and marketplace links |
| `js/api.js` | TCGdex API, cached on the device in IndexedDB; card details from the shipped details file first |
| `js/details.js` | Reads (and packs) the card details file `data/details-*.json` |
| `sw.js`, `js/offline.js` | Service worker: offline use, quick starts on bad connections, keeps the big files |
| `js/assets.js` | List of the big files (generated by `tools/assets.mjs`) |
| `js/backup.js` | Backup file format, Home Screen tips, asking the browser to keep the storage |
| `js/app.js` | User interface |
| `bench.html`, `bench-page.js` | Hidden speed test page (not linked from the app), see below |

### Big files, offline use and app updates

Files under `models/`, `vendor/` and `data/` (text-recognition models, their runtime, the card details) are *versioned*: a new version always gets a new folder or file name (`models/ppocr-v6tiny-2/`, `data/details-<hash>.json`), and a published file is never changed in place. The service worker (`sw.js`) downloads them in the background after the app opens, checks each one against the size and SHA-256 listed in `js/assets.js`, and keeps them in a cache that app updates never empty; saved versions that are no longer listed are deleted. After adding, replacing or removing such a file, run `node tools/assets.mjs` (the unit tests fail until `js/assets.js` matches the files). New scripts, styles or icons must be added to `SHELL` in `sw.js` (the unit tests check this too).

The rest of the app (the "shell") is kept as one complete copy of one version. Each start checks for a newer version for up to 2 seconds; on a slow or missing connection the saved copy opens, the newer one is used from the next start, and the page offers to reload.

### The card details file

The second ranking pass compares what the camera read with each candidate's HP, attack and ability names, illustrator, rarity, regulation mark and trainer text. These come from `data/details-<hash>.json` (about 0.3 MB to download, 2 MB in memory), so ranking needs no download, even offline; only cards newer than the file are looked up on the TCGdex API. To refresh it (for new sets):

1. In the private test-photo repo, run the **Snapshot card details** Action (it saves `catalog/details.json.gz`, public TCGdex data only), then pull.
2. Here: `node tools/build-details.mjs ../pokemoncards-testphotos/catalog/details.json.gz`. It writes the new `data/details-<hash>.json`, deletes the old one and updates `js/assets.js`.
3. `npm test`, then commit `data/` and `js/assets.js` together.

`node tests/rank-eval.mjs --offline --details data/details-<hash>.json` replays saved bench reads with no network but the shipped file: it should give the same result as the online run.

### Measuring

**On the phone: the speed test page.** Open `https://<your-username>.github.io/<repo-name>/bench.html` (it isn't linked from the app), reload it once, tap **Run** and keep the screen on for a minute or two, then tap **Copy results** and paste them into the chat. It records the phone and browser (iOS / Safari version, processor cores, WebAssembly SIMD, WebGPU, storage, which of the app's big files are saved), the camera's real resolution (it opens the camera once, takes no picture), how long the card list, card details file and text reader take to load, and timed scans of five sample cards (public TCGdex pictures, drawn ones when offline) as camera scans and as photos, the first time and again: tap to result, finding the card, reading the text, matching, and the stamp check. Also the text reader's memory (after six whole-card reads too), its restart after being stopped when idle, and a search speed test. It says which text reader ran (PP-OCR, or Tesseract where PP-OCR can't run). If the phone reloads the page during a run (out of memory), opening it again shows what was measured until then. `?samples=2&passes=1` makes it shorter, `?camera=0` skips the camera, and `?reader=tesseract` measures the Tesseract reader the app used before PP-OCR (still its fallback), for the before-and-after comparison. `node tests/e2e-bench-page.mjs` checks it in Chromium.

**Accuracy on labelled photos** (the private test-photo repo):

```bash
node tests/bench.mjs --photos ../pokemoncards-testphotos --split dev --out bench.json   # the real app in Chromium
node tests/rank-eval.mjs --bench bench.json --photos ../pokemoncards-testphotos --split dev --by-version  # re-ranks saved reads in seconds
```

Both score the card (top 1 / top 5) and the **printing**: the version the result sheet would show first for the best match (1st Edition, shadowless, reverse holo, set-logo and other stamps, picked the way `js/stamps.js` picks it from the stamps read on the artwork), against the photo's labelled version. "Right card + printing" counts only photos whose label names a printing TCGdex lists (a card printed only one way counts when the card is right; "unknown" labels, labellers who disagree and printings TCGdex doesn't list are left out); "version picked right" counts the right cards printed more than one way, where the pick matters. The details snapshot has no prices, so every printing counts as priced. See `tests/printing.mjs`.

Photos are split into a dev half (tune on it) and a holdout half (check it once, at the end) by a hash of the photo id. `--split-by card` hashes the card id instead, so every photo of a card falls in the same half: use it for new, clean holdouts (the default split stays the one every number so far was measured on; with it, most holdout photos show a card that also has dev photos).
